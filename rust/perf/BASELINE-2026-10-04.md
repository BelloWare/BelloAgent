# Rust session streaming baseline — 2026-10-04

## Finding

The current real Rust path keeps up with the tested 100-message / 100,000-character
fixture, but its cost scales with archived message count. Every 16-byte delta
rewrites and synchronizes the entire session. Its unbuffered JSON serializer makes
6,150 write syscalls per chunk at 100 messages. Increasing message count to 1,000
while holding total text constant raises that to 59,250 writes per chunk and
creates seconds of streaming backlog. Shared-snapshot reads themselves stay small;
that does not make whole-session persistence and publication cheap.

No optimization was implemented, and no Rust-vs-Swift speedup is claimed.

## Primary measurements

Three processes per case; 500 chunks/process; 100 messages × 1,000 ASCII characters;
16 bytes/chunk; offered 100 Hz. Exactly 8,000 new text bytes/run. Each latency pool
contains 1,500 samples and uses nearest-rank percentiles.

| Measured interval | Filesystem | p50 ms | p95 ms | p99 ms | max ms |
|---|---|---:|---:|---:|---:|
| `SessionStore::transact` | overlay | 2.034 | 2.286 | 2.686 | 3.893 |
| Fixture send start → first Controller watch observation | overlay | 2.446 | 3.016 | 4.598 | 24.659 |
| `SessionStore::transact` | tmpfs | 1.107 | 1.321 | 1.598 | 2.698 |
| Fixture send start → first Controller watch observation | tmpfs | 1.277 | 1.519 | 1.849 | 4.977 |

All primary Controller runs preserved all chunks, had zero coalesced chunk
observations, reached the final exhausted-queue revision, and passed reopen/content
validation. The watch event timing is an observation upper bound on publication;
it is not a direct timestamp inside `publish()`.

Every store run had exactly:

- 3,075,000 write syscalls, **6,150 per chunk**, from `/proc/self/io` `syscw`
- 59,056,894 logical snapshot bytes written, exactly matching `wchar`
- **7,382.11× write amplification** relative to 8,000 new text bytes
- Initial active snapshot 114,104 bytes; final active snapshot 122,106 bytes
- Overlay Linux `write_bytes` accounting about 60.10 MB; tmpfs reported zero
  block-write bytes despite the same logical writes

The primary store processes used 20.43–21.03% of one CPU on overlay and 11.42% on
tmpfs. Overlay store CPU time was 0.11–0.13 s user plus 0.91–0.92 s system over
roughly five seconds. The high system-time share and syscall count are consistent
with substantial unbuffered serialization cost. They do not isolate the exact
wall-time contribution of each syscall or prove a particular future speedup.

Controller aggregate CPU was 24.37–27.77% on overlay, 13.20–13.40% on tmpfs; these
figures include its local HTTP fixture and observer. Process-lifetime peak RSS was
3,440–3,660 KiB for store and 6,176–6,700 KiB for Controller across the primary
cases. These peaks include startup/seeding, not only the measured interval.

The observed `snapshot_shared()` Arc-read p99 was 0.340–0.421 microseconds per
overlay run (0.311–0.350 microseconds on tmpfs). That short read does not measure
creation of the published snapshot, layout, paint, GPU execution, compositor
presentation, or what a person sees.

`strace` was attempted separately for syscall categorization but container ptrace
was denied (`PTRACE_TRACEME: Operation not permitted`). No bypass was attempted.
Its failed invocation and stderr are retained. The successful, untraced
`/proc/self/io` counts are the syscall evidence; there is no syscall-time profile.

## Separate message-count stress case

One process per mode, overlay, 1,000 messages × 100 ASCII characters: the same
100,000 retained text bytes, but more message metadata. Same 500 chunks at 100 Hz.
This stress run is not pooled into the primary distribution.

| Interval | p50 ms | p95 ms | p99 ms | max ms |
|---|---:|---:|---:|---:|
| Store transaction | 17.417 | 18.678 | 19.869 | 20.566 |
| Fixture send start → Controller watch observation | 3,049.589 | 5,494.601 | 5,716.549 | 5,772.137 |

The store took 8.661 s to process the nominal five-second workload; Controller took
10.852 s to drain it. The store issued 29,625,000 writes (59,250/chunk), wrote
119,131,894 logical bytes for 8,000 new bytes, and consumed 99.87% of one CPU.
Controller aggregate CPU was 102.19% (multiple threads plus fixture), its
process-lifetime peak RSS was 9,424 KiB, and all chunks/reopen checks passed.
The raw socket-send schedule records the finite offered load independently of the
Controller backlog.

Ten times as many messages caused nearly ten times as many write calls, while
snapshot size only roughly doubled. This is the most useful evidence for tackling
fragmented serialization before drawing conclusions from fast Arc reads.

## Source-backed improvement plan (not implemented)

1. **Buffer the existing snapshot writer first, preserve semantics.**
   `session.rs:480–529` clones the complete Session, passes the unbuffered `File`
   directly to `serde_json::to_writer`, syncs it, renames it, and syncs the directory.
   Introduce a bounded serialization buffer or `BufWriter`, explicitly flush it
   before file sync, and preserve the existing pre-rename rollback / post-rename
   uncertainty behavior. This is the smallest independently measurable change;
   it does not solve whole-history byte amplification. Rerun this exact fixture
   and its failure tests before claiming an improvement.
2. **Use versioned append-only journal records for durable changes.**
   Record command/queue/edit identities and streaming appends with a monotonic
   revision and parent/sequence linkage; validate bounded records and stale reply
   identities on replay. Serialize one bounded record, append it, then sync at the
   promised durability boundary. Start with per-delta durability equivalent to the
   current contract; batching or acknowledging before sync would be an explicit
   policy change, not an invisible optimization. Preserve exclusive ownership,
   poison uncertain writes, recover incomplete trailing records without ignoring
   middle corruption, and atomically checkpoint/compact with directory sync.
   Existing v1 snapshots need an explicit, idempotent migration/recovery story;
   do not silently claim compatibility with Swift journals.
3. **Publish immutable history plus a versioned live-row delta.**
   `runtime.rs:84–92,181–193,289–300` deep-clones a full store snapshot on every
   persisted delta before publishing an Arc. Sharing immutable archived rows and
   appending only to the active row removes that repeated history clone. Readers
   should carry generation/base revision and get a full bounded resynchronization
   on cursor gaps or reset. Do not send lossy individual appends through a
   coalescing watch channel without a recoverable cursor or cumulative state.
4. **Borrow the Swift structure, not unverified performance claims.**
   `SessionStreaming.swift:16–51` appends text/thinking in memory and journals
   response-ledger boundaries rather than each text fragment.
   `SessionStreamingRow.swift:24–39,85–119` caches segments by revision and produces
   UTF-8 suffixes / revisioned part appends.
   `SessionJournal.swift:197–239` encodes each append once, uses an append-only
   locked file, exposes batching via `flush`, and poisons failed writes/syncs.
   These are design references. Swift's partial-stream persistence boundaries are
   not identical to the Rust per-delta durable snapshot contract and need an
   explicit decision before adopting its batching behavior.
5. **Verify failure semantics and instrument separate latency stages.**
   Keep tests for stop/retry, held queue edits, duplicate identities, stale deltas,
   partial-stream replay exclusion, failed append/sync, torn tail, corruption,
   reopen, checkpoint crash windows, and slow/coalescing subscribers. Add explicit
   timestamps at receive, committed, published, layout/paint, and actual present
   if GUI latency is the next target. The current data measures only the first
   path through watch observation; it cannot establish screen presentation time.

## Validation and limits

The harness compiled in release mode. Its smoke run passed after correcting the
harness's terminal-worker synchronization (described in README). All 12 primary
runs and both stress runs completed within finite deadlines. Every Controller
case verified its final content after reopening storage. Raw failed initial smoke
and denied tracing artifacts are retained separately rather than treated as
successful measurements. This work touched only `rust/perf/` and the standalone
benchmark example; no core implementation or Cargo manifest was edited.

All 25 existing core tests passed in release mode: 18 unit tests, two runtime
integration tests, and five transport tests. The exact command was
`cargo test --manifest-path rust/Cargo.toml --locked --offline --release -p
bello-agent-core`; its full output (retained locally; not published)
is retained. These are existing tests, not a claim that every failure mode proposed
above already has coverage.
