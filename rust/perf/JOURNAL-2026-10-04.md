# Journal candidate — independent safety review and measurements

## Result

The final journal candidate passed the independent review of the reported
persistence-admission issues and all 41 release core tests. On the unchanged
100-message / 100,000-character Controller fixture, overlay send-to-watch p95 fell
from **0.495 ms** for buffered full snapshots to **0.230 ms** for the journal.
Aggregate process write-character accounting fell from about **59.67 MB** to
**0.703 MB** per finite 500-chunk run. All Controller samples preserved every chunk,
reported zero coalesced chunk observations, and passed reopen validation.

This measures real loopback SSE -> Controller -> durable storage -> watch
observation, not display presentation. The journal reduces full-history write
amplification; publication still deep-clones a whole Session.

## Controller results: buffered full snapshots → journal

Primary pooled samples: n=1,500 per case; nearest-rank percentiles.

| Filesystem | p50 ms | p95 ms | p99 ms | max ms |
|---|---:|---:|---:|---:|
| Overlay, buffered | 0.355 | 0.495 | 0.705 | 3.940 |
| Overlay, journal | 0.147 | 0.230 | 0.334 | 1.760 |
| Tmpfs, buffered | 0.241 | 0.423 | 0.837 | 3.927 |
| Tmpfs, journal | 0.150 | 0.263 | 0.434 | 2.741 |

The observed overlay p50/p95 ratios are 2.42×/2.15× lower latency. These are
synthetic watch-observation ratios, not an app-wide speedup or exact timestamps
inside `publish()`.

For each primary overlay Controller run:

- Buffered aggregate `/proc/self/io` `wchar`: 59,667,088–59,667,672 bytes
- Journal aggregate `wchar`: 702,976–703,080 bytes, about 84.9× less
- Buffered aggregate CPU: 3.60–3.80% of one CPU
- Journal aggregate CPU: 1.60–1.80% of one CPU
- Journal process-lifetime peak RSS: 6,444–6,816 KiB
- Journal Linux `write_bytes` accounting: 589,824–593,920 bytes

Those counters include fixture HTTP and observer activity in both versions. They
are not isolated journal-file bytes, and Linux `write_bytes` is not physical-device
traffic. Tmpfs correctly reports zero block-write bytes. The main byte-volume
claim uses the same complete Controller process boundary in both candidates.

## Direct-store mode is a non-journal control

The unchanged `store` mode calls `SessionStore::transact` with `Session::delta`.
It does **not** call `append_delta`; no direct-journal result is claimed for it.
It remains useful as a full-checkpoint control:

| Primary store case | Buffered p50 / p95 | Journal-build control p50 / p95 |
|---|---:|---:|
| Overlay | 0.230 / 0.337 ms | 0.233 / 0.357 ms |
| Tmpfs | 0.143 / 0.263 ms | 0.168 / 0.244 ms |

Every new control run still makes 500 writes and rewrites 59,096,394 logical bytes,
versus 59,056,894 earlier. The exact 39,500-byte increase is 79 bytes of schema-v2
metadata × 500 checkpoint writes. Full checkpoint amplification persists for
accepted commands; streamed Controller deltas now use the append path.

## Safety review and verification

No remaining release blocker was found in the reviewed scope of the final
candidate. This is source/test evidence, not proof against every filesystem or
power-loss behavior.

Confirmed design properties:

1. A complete versioned record is encoded, appended and file-synced before the
   in-memory delta or publication. First creation also syncs the directory before
   publication. Setup metadata failures now poison the writer, preventing a later
   append from skipping first-create durability.
2. Live delta admission checks exact JSON-escaped text growth and decimal
   revision/sequence growth before any journal creation/append. The cached
   encoded size matches actual encoding across Text/Reasoning/Tool, escapes,
   multibyte Unicode, and counter boundaries in the regression test.
3. The hard encoded checkpoint limit remains 256 MiB. New streaming data and all
   accepted commands resulting in a running turn or held edit preserve 128 KiB
   for recovery/error metadata. Recovery accepts no new input and may consume
   that reserve. Rejected deltas/held-edit commands preserve disk and counters.
4. Checkpoints rotate generation only with durable snapshot commit. Before-rename
   failure preserves the old live journal; post-rename uncertainty blocks future
   writes and retains recovery evidence. Directory-open and directory-sync errors
   after rename both map to uncertainty. Old-generation cleanup occurs only after
   a durable checkpoint and is optional for correctness.
5. Replay validates record version, session, generation, sequence and active reply.
   It pauses an interrupted run, excludes partial output from provider replay,
   preserves an incomplete final line in the old generation, and refuses malformed
   complete records instead of silently dropping their contents.

All **41 independent release core tests passed**: 34 unit, two runtime and five
transport tests. Added coverage includes rotation, pre-/post-rename checkpoint
failures, stale delta rejection, valid-prefix/torn-tail recovery, v1 migration,
size-admission equivalence and rejection, first-create metadata failure, and
held-edit admission before/after reopening plus Cancel. Near-limit tests use an
injected smaller admission limit rather than allocating a 256 MiB fixture.

The initial candidate's checkpoint-size admission bug and a follow-up held-edit
reserve hole were reported and fixed before any timing or release approval.
Their review record is preserved. No performance evidence is attributed to those
rejected candidate hashes.

Remaining limits: the serializer's final size check occurs after allocation;
whole-history checkpoints/publication still copy or encode retained data;
journal replay can allocate within its bounded record/file limits; no physical
crash/power-loss test or GUI presentation measurement was run. A v1 file so close
to the hard cap that expanded v2 metadata cannot fit can be refused without
replacing its original snapshot. These are disclosed limits, not measured failures
of the ordinary fixture.
