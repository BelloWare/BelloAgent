# Buffered snapshot candidate — independent measurement and review

## Result

Pre-serializing the complete snapshot to a Vec before `write_all` removed the
fragmented write syscall bottleneck in these synthetic runs. On the primary
100-message / 100,000-character overlay fixture, observed store p50 fell from
2.034 ms to 0.230 ms (8.85× lower) and p95 from 2.286 ms to 0.337 ms (6.78× lower).
The full loopback Controller-to-watch p95 fell from 3.016 ms to 0.495 ms.

This is a measured local before/after for one persistence implementation change,
not an app-wide, Swift-relative, rendering, or presentation speedup. Whole-session
cloning and full snapshot byte amplification remain.

## Primary before → buffered measurements

All values are milliseconds. The Controller interval is socket-send start to the
first watch observation containing a chunk, including observer scheduling.

| Case | p50 before → after | p95 before → after | p99 before → after |
|---|---:|---:|---:|
| Store, overlay | 2.034 → 0.230 | 2.286 → 0.337 | 2.686 → 0.461 |
| Controller, overlay | 2.446 → 0.355 | 3.016 → 0.495 | 4.598 → 0.705 |
| Store, tmpfs | 1.107 → 0.143 | 1.321 → 0.263 | 1.598 → 0.376 |
| Controller, tmpfs | 1.277 → 0.241 | 1.519 → 0.423 | 1.849 → 0.837 |

Every 500-chunk store run changed from **3,075,000 write calls to 500** according to
`/proc/self/io`. Each transaction took one write call in this local fixture;
`write_all` is still allowed to make multiple OS calls on a partial write.
Both versions wrote exactly **59,056,894 logical bytes for 8,000 delta bytes**
(7,382.11×). The optimization changes syscall fragmentation, not the snapshot
format, logical write volume, or per-delta sync policy.

Primary overlay store CPU dropped from 20.43–21.03% to 2.40–2.61% of one CPU.
Controller CPU dropped from 24.37–27.77% to 3.60–3.80%, including fixture/observer
work. Candidate primary process-lifetime peak RSS was 3,556–3,796 KiB for store
and 6,432–6,892 KiB for Controller. This small fixture does not characterize the
new transient allocation cost for near-limit sessions.

All candidate primary Controller runs observed every chunk, reported zero
coalesced chunks, and validated complete content and Idle state after reopening.
There is still no GUI layout/paint/compositor/present measurement.

not be described as a thousands-fold intrinsic per-operation speedup.

## Independent correctness review

No new ordering regression found in the measured candidate:

1. `encode_snapshot` produces complete JSON plus its trailing newline before
   creating the temporary file. Serialization/size errors therefore occur before
   any candidate file is opened.
2. `file.write_all(&bytes)` completes before `file.sync_all()`. This uses no
   buffering destructor, so there is no accidental flush-after-fsync window.
3. Atomic rename still follows successful file sync. Directory sync still follows
   rename. In-memory state is assigned only after the complete write succeeds.
4. Tempfile `create_new`, 0600 mode, owner lock, pre-rename cleanup and existing
   post-rename sync-failure poisoning are retained.
5. The new 256 MiB encoded-size rejection avoids persisting a snapshot that the
   existing open limit would reject. It is not an allocation cap: the full Vec is
   already allocated before checking its length. This is a small new validation
   behavior as well as a buffering change.

All **26 independent release core tests passed** (19 unit, two runtime integration,
five transport). The new test checks newline/Unicode encoding roundtrip; existing
tests cover before-rename rollback, injected after-rename uncertainty and blocked
writes, owner exclusion, private file modes, queue/stop/retry behavior and transport
contracts. These tests do not inject every possible low-level short-write,
allocation, disk-full or power-loss failure. This review is source/test evidence,
not a physical crash-durability certification.

### Pre-existing gap reported separately

The measured candidate retains the earlier expression:

```rust
File::open(parent)?
    .sync_all()
    .map_err(|e| Error::PersistenceUncertain(e.to_string()))?;
```

A failure opening the directory after successful rename returns ordinary `Io`,
not `PersistenceUncertain`, so the store is not poisoned for that post-rename
failure. The buffering change did not introduce it. It was reported for a separate
fix mapping both open and sync errors to uncertainty, with a targeted regression.
That fix should preserve old memory/revision, leave the already-renamed disk
snapshot recoverable, and reject subsequent writes until reopening.

## Next justified work

Keep this conservative improvement and the separate uncertainty fix covered by
regression tests. Before changing journal semantics, measure larger retained text
and memory pressure: the current implementation still serializes/clones all
history and rewrites the same bytes. Versioned append journals and immutable
history/live-row publication remain the source-backed next architecture options,
with explicit durability/recovery and subscriber-gap contracts. The baseline
report describes that plan without assuming a measured benefit in advance.
