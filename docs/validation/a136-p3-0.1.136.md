## 3. Fork publication prefix

`AgentForkSeed.requirePublished(at:)` decoded every message through EOF on
each open/follow-up, although publication is the initial header, marker,
origin, inherited messages, context record and fork-seed reference.
The round-1 check read at most `ids.count + 5` records, returned at the validated
seed, and checked the file identity/size before accepting that prefix. Round 2
below replaces that record count with the writers' seed/turn order. It still
verifies the exact reference, ordered unique IDs, stripped consent,
inheritance metadata and content digest. Missing publication fails at the
publication boundary. Later history is validated by replay/recovery.

Child messages (`ChatMessage.id`), task inputs (`makeTurn`) and delivery row
IDs are fresh UUIDs, rather than counters restarted after the inherited rows.
There is no normal later-row reuse requiring a lifetime scan on every
publication check. `complete(rows:reference:)` keeps its duplicate-ID guard
in recovery, which already needs the full journal for turn/receipt/accounting
reconciliation; detecting an arbitrary duplicate later in a damaged journal
does require those later rows. Ordinary journal opens also retain
`JournalChainCheck`'s unique-ID/parent-chain validation.

## 4. Managed-child connection moves

The old rebind guard recognized only the v2 marker name. Promotion changes
the name, preserving the marker's generation field:

| Format | Marker kind | Child marker data | Durable origin |
| --- | --- | --- | --- |
| v2 | `pi-app.native.v2` | `version: 2` | `pi-app.subagent-origin.v1` |
| v3 | `pi-app.native.v3` | `version: 2` | same origin, plus steering turn records |
| v4 | `pi-app.native.v4` | `version: 2` | same origin with optional task/fork/cache fields; fork-seed and extended turn/delivery records |

V3/v4 owners and sides use the same marker names but retain `version: 1`.
Rebind now reads the initial marker and refuses version-2 children as well as
the original v2 marker. Round 2 below restricts that version check to native
marker kinds. It does not confuse an owner's family records with
child identity. V4's `pi-app.agent-fork-seed.v1` exists only for full forks;
fresh v4 children are also refused. The shared `pi-app.subagent-turn.v1`,
`pi-app.subagent-turn-state.v1`, `pi-app.subagent-turn-terminal.v1` and
`pi-app.agent-delivery.v1` records occur in family owners/mirrors too and are
not independent child markers.

## 5. Delivery-cost flake

Temporary projection invalidation logging reproduced the existing assertion
in isolated run 9 (`delivery-diagnosis-9.log`): delta 16 visited 301 rows.
The stack is `applySnapshotRows` → `messages.didSet` → `publishTranscript` →
projection invalidation. The projection context remained unchanged (running,
not loading, no queue or managed-child change); accounting revision was 1.

`delivery-revision-2.log` records the actual cause (run 2 of the additional
diagnostic set, delta 17):

```text
ACCOUNTING START revision=1 rows=301 figures=0
STREAM STALE messages=true accounting=0->1 figures=0
DELTA FAILURE index=17 visits=301 accounting=1
ACCOUNTING FINISH revision=1 changed=false figures=0
```

The stream guard used `accountingRevision`, a token advanced when an async
read **starts**, even if it returns no new figures. Starting the 100 ms
scheduled read during detached delta preparation therefore rejected an
otherwise current delta and rebuilt the whole resident page. This is an
unnecessary product invalidation, not real billing arriving and not turn
folding. Temporary logging was removed after tracing it.

`messageAccountingRevision` now advances only when the retained figures
change. Delta preparation/adoption use that token; query cancellation and
supersession still use the existing read revision. A real figures change
still prevents adopting stale accounting.

The deterministic regression prepares a real delta, completes an accounting
query across that prepare/adopt boundary, then applies the delta through
`applySnapshotRows`. An empty query must visit only the changed row; a real
query must preserve new figures on both resident and streaming rows.
`delivery-deterministic-red.log`: 1 test, 1 failure, **301 > 1** before the
fix. `delivery-mutation.log` changes the adoption guard back to the query
token and catches the same failure. The round-trip test's loop and one-row
threshold are unchanged; no warm-up or relaxed assertion was needed.

`restored-StreamingDeliveryCostTests.log`: **5/5 passed**. The original
`testRefreshRoundTripOccupancy` subsequently passed **20/20 separate
invocations**, each launching only that test, with no retries:
`delivery-isolated-01.log` through `delivery-isolated-20.log`.

## Lead review, round 2

Review base: pushed commit `49b65725`. This round changes only the helper
and its tests; the accepted app fixes retain their original commits.

### F1: only a native marker identifies a managed child

The round-1 guard treated any second record with `data.version: 2` as a
managed child. It now requires `JournalRecordKind.isMarker(customType)`
(`marker`, `childMarker`, `steeringMarker` or `codexMarker`) before trusting
that version. The existing v2 marker refusal remains.

The generated regression retains another tool's `version: 2` custom record
second and the native binding marker later in the chain. Check-only and
actual rebind now succeed, the saved binding opens on the new connection,
and the original journal prefix stays byte-for-byte intact. A purely
markerless pi journal already fails with `legacy_session` in
`SessionJournal`, before this guard; a second test preserves that existing
portable-handoff requirement rather than making legacy provider state writable.

`r2-rebind-red.log`: **15 tests, 3 assertions failed in the new move test**
(both requests refused and the binding stayed old). Removing only the
`isMarker` check reproduces all three failures in the single-test
`r2-rebind-mutation.log`. Restored `r2-final-ConnectionSwitchTests.log`:
**15/15 passed**, including the unchanged v2/v3/v4 child refusals and
main/side moves. `r2-final-HostServiceTests.log`: **10/10 passed**.

### F2: publication ends before execution, without a magic count

`requirePublished` no longer assumes a five-record overhead. It returns at
the validated seed and fails at the first `agentTurn`, the first message
past the inherited IDs, or EOF without a seed. Both `publishQueuedChild`
and `AgentFamilyRecovery` finish the seed before child turns/messages; the
reader and both writers now document that ordering. Adding publication
metadata does not change the boundary or cause a lifetime scan.

The new metadata test adds one record to the full publication prefix for
both empty and nonempty inheritance. The boundary test rejects seeds after
a turn (before or after the inherited messages) or an extra child message.
A missing seed followed by a turn and torn later data must fail with
`subagent_fork_publication` at the turn, before decoding the damaged tail.
The existing reference, order, content/digest, missing-row, consent and
later reused-ID recovery checks stay intact.

`r2-publication-red.log`: **12 tests, 5 assertions failed in the two new
tests**: two valid extended prefixes refused, two late seeds accepted, and
one torn lifetime tail read. `r2-publication-count-mutation.log` restores
`ids.count + 5`: **1 test, 2 failures**. `r2-publication-turn-mutation.log`
removes the turn boundary: **1 test, 3 failures**. All mutations are restored.
