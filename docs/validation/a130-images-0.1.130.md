## Boundaries and fixtures

Every image is generated in the test: ImageIO encodes HEIC, TIFF, BMP, JPEG
2000, ICO, PSD, GIF/APNG animations, the 12–25 MB photos and the over-8 MiB
scan. ImageIO on macOS 14.8 decodes but cannot encode WebP or AVIF, so a
1 × 1 lossless WebP, a hand-built two-frame animated WebP and a 2 × 2 AVIF are
embedded bytes, each checked against ImageIO before use (no format was
skipped on this Mac). Mislabeled and unreadable files are generated bytes.
Pasteboards are private named boards; the drop test uses its own dragging-info
double, so those classes stay in the parallel lane. The chooser test answers
through `PiQuestion.chooseFiles`; no panel is shown. Workspaces use
`MemoryVaultStorage`. No installed app, real chat, preference, Keychain,
credential, capture, provider request, release, tag or integration-branch write
is involved. Serial-lane and gallery runs held the shared full-lane lock.

## What changed

| Entry point | Before | Now |
| --- | --- | --- |
| Attach Images… (`attachImages`) | Panel offered PNG, JPEG, GIF, WebP; files went straight to inspection: other formats, mislabeled files and anything over 8 MiB were refused | Panel offers `UTType.image`; chosen files take the same preparation as paste and drop (`importImageFiles` → `ComposerTextView.prepareImageFiles`), counted as an import from the choice and refused if the draft changes meanwhile |
| Paste of files, drag-and-drop | Passed through by **extension** (`.png/.jpg/.jpeg/.gif/.webp` ≤ 8 MiB), so a `.jpg` holding HEIC was refused later; other image files converted | Decided by **content** (the helper's own 12-byte signature test) after ImageIO confirms the file is a readable image |
| Paste of image bytes | Unchanged | Unchanged |
| Helper `PiImage.process` | Animated GIF/WebP/PNG sent as they were | Sent as their first frame, PNG, with a hint (attachments, read results, tool images) |
| Helper `read` tool | HEIC, TIFF, AVIF, JPEG 2000, … failed as `binary_file` | Converted like pi converts BMP; see the parity rules below |

`prepareImageFiles` (one function for all three file entry points):

1. A regular, non-empty file whose first frame ImageIO can read (width and
   height); otherwise `“<name>” could not be read as an image. Attach a JPEG,
   PNG, HEIC, TIFF, GIF, WebP or other image file.`
2. A PNG, JPEG, GIF87a/89a or RIFF/WEBP signature up to 8 MiB keeps its
   original path and bytes, and goes through `AttachmentRecord.inspect` once,
   as before; its integrity refusals are never retried as conversion.
3. Anything else (HEIC/HEIF, TIFF, BMP, AVIF, JPEG 2000, ICO, camera raw, a
   mislabeled file, an original over 8 MiB) becomes a PNG in the app's
   `PastedImageStorage` under the generation lease, named
   `pasted-<generation>-<uuid>.png`, so the pasted-image sweep keeps it while
   a draft, queue or journal refers to it.

The composer chip, edits and the sent message use that path exactly as for a
pasted image; the transcript's user row still shows its image (its label comes
from the image blocks the helper loads from the attachment path).

## Decisions

- **Helper contract unchanged:** four images, 8 MiB each, 16 MiB per
  submission, PNG/JPEG/GIF/WebP signatures with matching MIME and digest. The
  app converts to fit it; no reason to widen it was found.
- **Originals over 8 MiB start at the helper's 2,000 pixels**, as a clipboard
  PNG over 8 MiB already did ("like oversized pastes", as briefed). A full-size
  PNG of a large photo cannot fit and costs seconds; the output is the same.
  Measured below. Conversions of files up to 8 MiB keep the existing order
  (full size first), so e.g. a 12 MP iPhone HEIC under 8 MiB converts as a
  Finder HEIC paste did.
- **Readability check for native signatures.** A file that looks like a PNG
  or JPEG but that ImageIO cannot read is now refused at attach time with the
  named message, instead of attaching and later reaching the model as pi's
  "could not be resized" placeholder.
- **Animated images stay original in the app; the helper sends the first
  frame.** One place covers attachments, the read tool and MCP tool images.
  APNG is treated like animated GIF/WebP. The hint is `[Image converted from
  animated image/gif to image/png; only its first frame is shown.]`.
- **Read tool fallback is conservative.** Only when pi's sniff finds no image
  and the first bytes are not valid UTF-8 (the text read's own test, so no
  text file changes); never for pi's own five formats (APNG and JPEG-LS keep
  pi's binary verdict), nor for TGA/PICT, which ImageIO detects heuristically
  (of 60,000 random headers, half shaped like TGA's, ImageIO typed 21 as TGA
  and none as anything else; common binaries were typed as nothing); and only if
  ImageIO can read the whole file, otherwise `binary_file` exactly as before.
  The 16 MiB image limit, the tool description and the `binary_file` message
  are unchanged.
- **Refusal wording.** The old "Supported image formats are PNG, JPEG, GIF
  and WebP" and "Select a regular image file up to 8 MiB" can no longer be
  reached by a prepared file except when it changes afterwards, so inspection
  now says `The image changed while it was being attached. Attach it again.`
  Inspection's GIF test now matches the helper's (GIF87a/GIF89a, not any
  `GIF8`).
- **CMYK JPEG normalization skipped.** No documented OpenAI rejection of CMYK
  JPEGs was found (a web search found only unconfirmed reports of JPEGs
  refused for other reasons), pi sends JPEG as it is, and verifying would need
  a paid live call, which is not approved. ImageIO reads CMYK JPEGs, so they
  attach as JPEG.

**Needs owner decision (optional follow-ups, not done):** a converted image's
composer chip shows its private file name (`pasted-….png`), as pasted images
already do; showing the original name would need a new attachment field.
Animated AVIF (`public.avis`) is not an image type to UTType, so the panel does
not offer it.

### Measurements

Generated noise photos, 4000 × 3000 at quality 0.9 (Debug app test, all three
entry points; `fixed-app-parallel-classes-final.log`, base from
`failing-first-app.log`):

| File | Base (paste/drop) | Now (chooser, paste, drop) | Stored PNG |
| --- | --- | --- | --- |
| 14.4 MB JPEG | 2.03 s / 1.87 s | 0.81 s each | 1125 × 844, 2.25 MB |
| 14.4 MB HEIC | 8.94 s / 8.70 s | 6.62–6.69 s | 1125 × 842, 2.18 MB |

Optimized standalone probe of the same loop on a smoother photo-like 6000 ×
4000 image: 16.5 MB JPEG 2.57 s → 0.46 s, 18.0 MB HEIC 7.70 s → 3.94 s, both
producing the same 1500 × 1000 PNG. In this shell ImageIO logs
`IOServiceMatchingfailed for: AppleM2ScalerCSCDriver` (no hardware scaler), so
HEIC times are pessimistic. Pure noise is the PNG worst case; smoother photos
keep more pixels within the helper's 4.5 MB base64 bound.

### Adversarial self-review

- Text files: the read fallback runs only on bytes the text read would refuse,
  with the same complete-scalar UTF-8 test; text that starts like `icns`,
  `II*\0` or `8BPS` still reads as text (test).
- Nothing passed through can fail the helper's own check: the pass-through
  test is the helper's signature test (`loadImages`), and ImageIO must also
  read the file first.
- The import counter covers the whole chooser path (choice → preparation →
  inspection), so the pasted-image sweep cannot collect a copy being prepared.
- An edit switch during preparation refuses the image (test), as paste does.
- No change to clipboard-byte pastes, the sweep, the leases or the helper's
  limits; the read tool's 16 MiB bound and its description are unchanged.
