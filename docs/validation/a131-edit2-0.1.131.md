## Cause and reproduction

EDIT-1 put the question in the composer immediately, but Send still waited
for its original input and checks. A helper opened from `.jsonl.meta` called
`loadFullHistory()` in `session.edit.prepare`, parsing and retaining every
reply; a second Edit joined that work. The app applied a 30-second command
acknowledgement deadline to that read. With no helper holding the chat,
`HistoryReader.editTarget` indexed the journal synchronously on the reader
shared by other chats. `turn.edit` independently required full history too,
so fixing preparation alone would move the same delay into Send.

The existing `MessageEditLatencyTests` harness writes 600/1,500 turns with
40 KB replies, compacts every 25 turns, then shows the chat in the real
isolated test window. Edit is pressed through the question's own pill. Its
new final case reopens the helper cold, presses Edit, then submits the edit
and waits for acceptance. This measures the durable acknowledgement, before
the replacement model reply. Each measurement restores the generated
`pristine-app-state`, so before and after start from the same journals.

## Change and preserved checks

`EditPreparationIndex` scans a cold journal for message/replay metadata and
original input offsets, using the existing journal reducer and edit planner.
It skips text, images, provider items and response presentation in ordinary
old messages and presentation-update records, keeping their actual source spans. It retains metadata, not hydrated old reply bodies. It checks
skipped JSON strings/numbers too; an unusual encoding or escape falls back
to the original parser. Family-delivery messages retain their original
content because family validation hashes it. Other records retain their
existing reducer/validation behavior, including state/receipt handling; unusual
message/custom-record hybrids fall back to the original reducer input.

Further reads reuse the index, catching up only appended records. A read
overtaken by a run keeps its scanned prefix for the retry, but returns no
preparation from a superseded head. Concurrent reads share a cancellable
load; a close/unload cancels its worker and fails waiting readers with
`session_closed`. A version read's full-history load does not hold an edit.
The selected original is read at its offset, or taken from its live retained
message. The same planner still computes `sourceTimeline`, `sourcePrefix`
and the replay plan; `sourceTextDigest` still hashes the exact original
display text. Pagination checks are unchanged.

Send reads the real inputs selected by that validated plan and the shown
suffix from its earliest context row. It publishes the existing branch and
queued replacement atomically before adopting anything. Earlier display
rows and hidden versions remain lazy through the existing partial-history
mechanism. Context, source checks, receipt ordering, spend, task records,
request links, stop/head guards and write-failure handling keep their
existing meanings. Version readers still restore the complete version store.
Chats with recorded agent-family state conservatively keep the existing
full-history Send path, whose tool-owner index also serves family recovery.

In the app, each retained edit reader owns its own offset indexes and actor;
the shared actor only routes the request. The cache is bounded like the
existing reader cache and is released on shutdown. Indexing does not decode
an unrelated turn merely to get the target. **Shared-file scope:** only the
edit entry point/cache and shutdown cleanup in `HistoryReader.swift`;
`SessionReads.swift`, history paging and `HistoryWindowPolicy` are untouched.

`session.edit.prepare` and `turn.edit` wait for the helper's reply or a
connection loss, without the arbitrary acknowledgement deadline. Other
commands keep their deadlines. No wire fields, capabilities, journal schema
or checkpoint schema change; no wire/concurrent/acceptance rerun is needed.

## Review round 2: replacement IDs (2026-10-23)

Astra's review of `01b3164c` found that a checkpoint-opened edit checked its
replacement ID only against resident messages and the bounded command
receipts. A fork has empty inherited receipts, so reusing an unloaded message
ID could commit a branch and write a duplicate message. Full replay refused
the same input with `duplicate_turn`.

`SessionBranching.edit` now also checks the replacement ID against the current
`EditPreparationIndex.replay.history`, which includes unloaded and abandoned
messages. This runs after ordinary submission validation, before resource
validation or any branch write. The existing head guards keep that index tied
to the edit's captured journal. No full replay or body hydration is added.

The new `EditPreparationTests.testColdForkRejectsReplacementIDsInUnloadedHistoryLikeFullReplay`
uses generated branched/compacted journals and actual forks with empty
receipts. Four collisions cover a summarized user, its assistant reply, a
replaced turn, and a retained message outside the fork's selected timeline.
Each is refused by full replay and by a checkpoint-opened helper, covering
both direct Send and cached preparation. The test checks `duplicate_turn`,
unchanged journal bytes/head, resident rows and receipts, an empty queue, and
continued partial history.
