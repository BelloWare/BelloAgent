## Reproduction and cause

The helper already sends `imageCount` in a user display row. The desktop
projector discarded it after substituting `Image` / `N images` for an empty
caption. The native user row had only text and skill pills, so a captioned
image disappeared visually as soon as it left the composer. History had the
encoded image blocks, but its display projection discarded their count too.

Before changing production code, a Release build of the base plus the first
two regressions ran `TranscriptImageTests` and `TranscriptImageRowTests`:
**2 tests, 5 assertion failures, 0 unexpected** (`evidence/failing-first.log`).
Both projections lost the count, neither row had image buttons, and the
image-only row drew `2 images`. The Release host's SHA-256 and base commit
are in `evidence/base-product.txt`.

## Implementation

- A user row keeps its image count and an explicit image-only flag. Its
  existing text, including the image-only copy/search description, stays
  intact; the visible text omits that description when thumbnails replace it.
- The optimistic Sending row keeps attachment **file references**, alongside
  its count. Its helper replacement and reopened history use the journal's
  image blocks, so deleting the original attachment does not lose the preview.
- Reopened pages attach a small immutable, boxed reference (path, row id, offset, length,
  device/inode). A live row resolves its offset only when a visible thumbnail
  asks, on an independent image history reader. A complete record stays
  readable while later records are appended or the last record is still
  being written; previewing neither repairs that tail nor starts a helper.
  No base64/data field enters
  the window's message array. Existing page/turn/window policies are unchanged.
- `TranscriptImageCache` is a serial background actor: it reads only the
  referenced record, validates the descriptor and row id, decodes base64 and
  uses ImageIO's immediate thumbnail decode with orientation applied. There
  is one transient read/decode at a time; the decoded-pixel LRU has a hard
  **16 MiB** pixel limit and **512-entry** limit (small images cannot keep
  accumulating keys/objects below the pixel budget). Thumbnails request 64 points at the backing scale; the
  viewer requests at most **2,048 pixels**, as Files does. Raw records and
  encoded image bytes are never cached. This is a cache bound, not a claim
  that total process footprint is 16 MiB.
- Each thumbnail has a **64 × 64 point** slot, with six-point gaps, before
  any bytes arrive. The grid wraps from count and width alone. Pixel arrival
  redraws the PiKit button without invalidating row height. Unmounted/hidden
  buttons cancel their request and release pixels; late completions are
  rejected. Mounted image bands check once after positioning, then on the
  clip view's bounds notifications; buttons also check after being unhidden
  or changing backing scale. Visibility uses the actual document viewport,
  rather than treating AppKit's sometimes larger `visibleRect` as the button.
  VoiceOver labels are `Image 1 of 2`, etc.; native keyboard and
  accessibility press use the same PiKit button action.
- A click opens a PiKit sheet with the **existing `FilePreviewView`** used
  by Files/Changes. `FilePreview` accepts a lazy journal image loader, so
  previewing publishes no temporary image file and opens no stock panel or
  external app. Errors stay visible in the thumbnail tooltip and viewer.

Shared-file touches: `WorkspaceModel.swift` adds two image-loader properties;
`WorkspaceRun.swift` adds three lines of Sending-row image metadata;
`ConversationPaneBridges.swift` forwards one lazy load action. The streaming
workstream's `TranscriptNativeDocument`, `SessionDisplay`, `TranscriptActivity`
and the paste/import/composer implementation are untouched. The generated
Xcode project includes the new files.

### Review: append-safe live lookup

Review found the first live offset lookup required a completely unchanged,
healthy journal. A helper appending another record during the lookup, or
halfway through its next record, could turn a complete earlier image into an
unavailable thumbnail. Two generated-journal regressions failed first with
**2 assertion failures, 0 unexpected** (`evidence/live-append-failing-first.log`).

complete user record it indexed; truncation is refused, and the decoder still

## Round 3: release image-reader indexes before termination

The re-review found that `ApplicationLifecycle.beginShutdown` awaited only
`model.history.releaseIndexes()`. The independent live-image reader could
therefore keep its temporary offset database until process exit. Shutdown
now also awaits `model.transcriptImageReader.releaseIndexes()` in the same
cleanup phase, before `model.shutdown()` and the successful termination reply.
This is one production line; no rendering, paging, storage format or UI changes.

The new `HistoryIndexFilesTests/testQuittingReleasesBothReadersIndexFilesBeforeAnswering`
uses a generated image journal and a model with a private state root and memory
vault. It creates one real index in each model-owned reader, records only the
new files bearing this test process's prefix, then drives the actual idle-quit
delegate with `answerTermination`. Both files must be gone at that callback;
both reader counts must be zero while the model is still held alive. An
expectation awaits the callback, without sleeps or elapsed-time assertions.
The fixture explicitly releases readers even on a failing run before removing
its generated state root.
